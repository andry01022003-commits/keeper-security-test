- **IP-conditioned permission rules and audit-row client IPs no longer trust an X-Forwarded-For address the backend cannot verify** (#4681, GHSA-59x8-r6jj-x95h). For a request whose TCP peer is inside `RATE_LIMIT_TRUSTED_PROXY_CIDRS`, the client IP resolved from `X-Forwarded-For` was used for `allowed_cidrs` permission conditions (#1849) and for the client IP recorded in audit rows. That address is only reliable when every trusted proxy appends the peer it received the request from, which the backend cannot check. The new `XFF_TRUSTED_FOR_AUTHZ` setting (default `false`) decides whether it may be used for these purposes. With it unset, a request through a trusted proxy has an unknown client IP for authorization and audit: IP-conditioned grants do not match it and are denied, unconditioned grants are unaffected, and audit rows record no IP. A request whose TCP peer is not a trusted proxy still uses that peer. Rate limiting, the upload guard and download telemetry keep resolving the client from `X-Forwarded-For` as before. Startup logs a warning when `RATE_LIMIT_TRUSTED_PROXY_CIDRS` is set and `XFF_TRUSTED_FOR_AUTHZ` is not. **Deployments behind reverse proxies that use `allowed_cidrs` conditions or rely on audit-row client IPs should set `XFF_TRUSTED_FOR_AUTHZ=true`, but only after confirming that every proxy in the trusted ranges appends or overwrites `X-Forwarded-For` with its own peer address.** Behind SNAT that hides the client address before the first proxy, no setting recovers the client IP, and a condition covering the proxy, node or pod ranges matches every proxied request. See `.env.example`.
