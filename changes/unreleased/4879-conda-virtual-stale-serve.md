section: Fixed

- **A virtual conda channel merges each subdir once for every encoding and keeps serving the previous merged repodata while it rebuilds** (#4879). `repodata.json`, `.zst` and `.bz2` of one subdir were three independent merges (three member fetches, three merges, three encodings), and when a remote member's cached repodata expired the kept merge was dropped, so every request waited on a full rebuild: about 45 s for a conda-forge `linux-64` `.bz2`, which ended in `merge shed` 503s and client timeouts when a dozen subdirs refreshed at once. The merged `repodata.json` is now kept once, zstd-encoded, and `.json` and `.bz2` are derived from it on first demand and kept with it (each encoding keeps its own ETag; the plain `.json` of a virtual is now compact JSON). A kept document that is no longer fresh is served at once, with `Warning: 110`, while exactly one background merge rebuilds it, and the next request after the rebuild gets the new document, with the encodings the previous one had been asked for already built. The new `CONDA_VIRTUAL_MERGE_MAX_STALE_SECS` (default: the merge cache TTL) bounds how long after it was first found stale a document may still be served; `0` restores waiting on the rebuild. A merge with a failed member is never served stale. Stale serves count as `ak_conda_virtual_merge_cache_hits_total{via="stale"}`. See `docs/operations/conda-virtual-merge-memory.md`.
