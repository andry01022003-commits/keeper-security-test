- **Deleting a repository answers 202 with a job instead of running the delete in the request** (#4311). `DELETE /api/v1/repositories/{key}` now records a job, renames the repository out of the way at once (its key no longer resolves, it leaves the repository listing and the key can be reused) and answers `202 Accepted` with the job and a `Location` of `GET /api/v1/repository-deletions/{id}`, which reports progress in the shape of a migration job. A background worker deletes the rows in batches of 500 and reclaims the storage under a cluster-wide row claim, so one replica runs each job and another resumes it if that replica dies. Before, the key collection and the database cascade ran inside the request, and a repository of 10,000 or more artifacts behind a proxy timed out (504 or `SERVICE_UNAVAILABLE`). The repository delete also hands its objects to the GC journal and re-checks references before each delete. Clients that expected `200` from the delete should accept `202`. The `repository.deleted` event is emitted when the job completes. Migration 304 adds `repository_delete_jobs`. See `docs/operations/repository-delete.md`.
