- **A remote (proxy) repository can now keep serving its cached copy when upstream answers 404 or 410, instead of deleting it, via `on_upstream_not_found = keep`** (#4640). Until now a stale mutable entry whose upstream revalidation answered 404/410 had its cached body deleted and the path negative-cached — correct when upstream is the source of truth, but destructive for deployments that use the proxy cache as a continuity copy of an external registry that may retract content. The new per-repository policy, settable with `PUT /api/v1/repositories/{key}/on-upstream-not-found` and readable with `GET`, defaults to `delete`, which is today's behaviour, so nothing changes until an operator opts in. With `keep`, a definitive 404/410 serves the cached bytes on both the buffered and streaming fetch paths, on the conditional `HEAD` revalidation probe, and to the npm computed-packument cache; a path that was never cached still returns 404 and is negative-cached, and the Package Age Policy, quarantine and lifecycle gates still apply to a kept copy. The TTL is deliberately left unextended so a later upstream 200 re-publish is picked up, and `ak_proxy_kept_on_upstream_not_found_total{repository}` counts every kept serve so content that no longer exists upstream is listable.
