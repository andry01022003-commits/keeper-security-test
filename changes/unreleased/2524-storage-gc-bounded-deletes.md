- **Storage GC no longer holds a database transaction across object-store deletes, and a pass can be budgeted** (#2524). Every sweep (soft-deleted artifact keys, OCI blob sweep, objects left by repository deletes, abandoned OCI uploads, orphaned Maven objects) now claims a candidate in a short transaction that removes its rows and records the delete in flight, commits, and only then deletes the object, with up to `STORAGE_GC_DELETE_CONCURRENCY` (default 4) deletes at once. A failed or interrupted delete stays recorded and is retried by a later pass; a key that gained a reference in between is kept. The check before each delete also counts revision history, so the newest revision of a trashed artifact in a versioning-enabled repository keeps its bytes instead of being left pointing at a deleted object. An OCI push of a digest whose blob is being deleted at that moment is answered 503 ("retry the upload") instead of committing a row for deleted bytes. New per-pass budgets `STORAGE_GC_MAX_KEYS_PER_RUN`, `STORAGE_GC_MAX_BYTES_PER_RUN` and `STORAGE_GC_MAX_RUN_SECS` (default 0, unlimited) stop a pass early and report it as `budget_exhausted` in the GC result, and new `ak_storage_gc_*` metrics count deletes, failures, skips, budget stops and the retry backlog. The GC result's `bytes_freed` now counts the soft-deleted artifact keys it reclaims; it read 0 for them before because the per-key byte sum was decoded with the wrong type. See `docs/operations/storage-gc.md`.
