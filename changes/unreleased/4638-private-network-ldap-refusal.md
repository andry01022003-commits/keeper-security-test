- **Refusing an LDAP server, identity provider, upstream or webhook on a private network now names the setting that admits it** (#4638). Saving `ldap://10.10.10.10:389`, or an `ldaps://` hostname that resolves to a 172.16.x.y address, failed with "is not allowed (private/internal network)" and nothing else, so an operator with a directory server on an internal network had no way to save or edit the configuration. The outbound-URL guard already had an allowlist for this case, `AK_SSRF_ALLOW_PRIVATE_CIDRS` (comma-separated CIDRs or IPs, shared by the upstream, migration, LDAP, SSO/OIDC/SAML and webhook paths), but no refusal mentioned it. The refusal for an RFC 1918, CGNAT or IPv6 unique-local address now names `AK_SSRF_ALLOW_PRIVATE_CIDRS` with the refused address as the example (plus `WEBHOOK_ALLOW_PRIVATE_IPS` / `SSO_ALLOW_PRIVATE_IPS` on those surfaces), on both the save path and the LDAP connection test. Cloud metadata (169.254.169.254 and its IPv4-mapped IPv6 form, `fd00:ec2::254`, 192.0.0.192, 100.100.100.200), loopback and link-local addresses stay refused even when a containing range is listed, and their refusal no longer suggests a setting (the SSO refusal previously did). `.env.example` and the startup log now say the list applies to LDAP and the other outbound surfaces, not only upstream URLs.
