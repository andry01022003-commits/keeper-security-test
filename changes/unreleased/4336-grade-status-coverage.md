section: Changed

- **Repository security grades report what was assessed instead of an F floor** (#4336). A failed scan (#2167) or an archive no scanner could catalog (#4036, #4154) used to force a repository's grade letter to F while its score stayed 100, which mixed "known bad" with "not assessed" and changed no gate. Repository scores now carry `grade_status` (`rated`, `incomplete` or `unrated`) and `coverage` (artifacts, scanned, cataloged, partial, failed, uncataloged, `coverage_pct`); `grade` is the letter over the assessed artifacts and is `null` when the repository is `unrated` (nothing assessed, including no scans at all). For a `rated` repository the letter is exactly the one earlier releases showed. Each scan row carries `grade_status` and `grade_status_reason` in the same vocabulary, so a `partial` scan reads `incomplete` with its reason. The security dashboard adds `repos_rated`, `repos_incomplete` and `repos_unrated`; `repos_grade_a` and `repos_grade_f` now count shown letters, so a floored repository is no longer counted as F. Deleting an artifact now recalculates its repository's score, so removing the archive that could not be cataloged makes the repository `rated` without waiting for the next scan.

  Client impact: `grade` on `GET /api/v1/security/scores`, `GET /api/v1/repositories/{key}/security` and the external-findings ingest response is now nullable and never the F floor. Clients that treated an F as "not assessed" should read `grade_status`. Migration 303 adds nullable columns only; during a rolling upgrade 1.11 replicas keep reading and writing the `grade` column exactly as before (it still carries the floor), and a score a 1.11 replica wrote is read by 1.12 with its status derived from the stored flags until the next recalculation.
