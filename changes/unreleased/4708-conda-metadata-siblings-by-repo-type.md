section: Fixed
issues: [#4708]

- **Remote and virtual conda channels serve real `current_repodata.json`, `run_exports.json` and `repodata.json.sig`, and `patch_instructions.json` is proxied or 404 instead of an empty stub** (#4708). `repodata.json` branched on the repository type, but its four sibling documents did not: they were always built from the repository's own package rows, which a remote or virtual repository does not have. conda (classic solver and libmamba) requests `current_repodata.json` first and only falls back to `repodata.json` on a 404, so it took the empty 200 as an empty channel and resolved nothing while pixi and rattler worked; `run_exports.json` was silently empty for conda-build and rattler-build; and a virtual's `repodata.json.sig` was a valid signature over a document the client never downloads, bypassing the allowlist and name-ownership merge. A remote channel now proxies its upstream's `current_repodata.json`, `run_exports.json`, `patch_instructions.json` and `repodata.json.sig` through the same capped, budgeted fetch as `repodata.json`, passing an upstream 404 through as 404, and never signs upstream content with its own key. A virtual channel derives `current_repodata.json` from the merged `repodata.json` it serves (the newest version of each package plus the newest builds that satisfy dependencies the kept records leave unmet, as conda-index does), merges `run_exports.json` over its members under the same allowlist and hosted-name ownership rules, signs the merged `repodata.json` bytes with its own key, and applies the existing member-failure policy (502, or a partial document when the virtual allows one) to all three. Hosted channels are unchanged except for one behaviour change: `patch_instructions.json` on hosted and virtual channels now answers 404 instead of an empty 200, which falsely asserted that the channel has no patches. The `/t/<token>/` routes share the same handlers.
