- **Refused logins, permission-condition decisions and external findings ingests now leave a trace, and a trusted gateway's `X-Request-ID` becomes the correlation ID** (#4677). A login refused 429 by the login limiters (`/api/v1/auth/login` and `/v2/token`) wrote nothing but a metric; it now writes a `LOGIN_RATE_LIMITED` audit row (the attempted username, path, limiter and verified client IP, never the password) and a `security` warning, at most once per source IP per limiter window so a flood cannot become an audit-table flood. Permission decisions that evaluate an `allowed_cidrs` condition (#1849) count `ak_permission_condition_evaluations_total{condition,outcome}` (`matched`, `not_matched`, `unknown_ip`) and log at debug. A successful `POST /api/v1/security/findings/external`, the write that classes a `MAL-*` advisory malicious, writes an `EXTERNAL_FINDINGS_INGESTED` audit row with the scanner, severity and class counts and the `MAL-*` ids, plus a `security` log line. An `X-Request-ID` of up to 128 visible ASCII characters from a peer in `RATE_LIMIT_TRUSTED_PROXY_CIDRS` is now the correlation ID (after an explicit `X-Correlation-ID`, before `traceparent`), so gateway access logs join backend logs and audit rows; from any other peer it is ignored as before. See `docs/operations/detection-signals.md`.
