- **Hosted conda channels serve a real JLAP, so conda and rattler update a cached index with a patch instead of downloading it again** (#4175). The JLAP was served only as `repodata.json.jlap`, while conda and rattler request `repodata.jlap` (the name conda-forge serves), and it named only the current index hash, so JLAP clients always fetched the whole `repodata.json`. It is now served under both names. Each new revision of a subdir is now recorded with its BLAKE2b-256, an RFC 6902 patch from the previous document is appended to a stored JLAP whose checksum chain continues from the stored bytes, and range requests from the client's saved position return only the new lines (`416` past the end). The last `AK_CONDA_JLAP_REVISIONS` (default 8) documents are kept per subdir (migration 305). `repodata.json.zst` and `.bz2` now decompress to exactly the bytes `repodata.json` serves, which the JLAP chain hashes; before, they held a compact rendering. Clients that read them see the same records, but the files are slightly larger (measured on a 30,000-record channel and on a 387,000-record one: about 4 % for `.zst`, under 1 % for `.bz2`), and decompress to about a third more bytes. The JLAP is recorded with the revision before its documents are served, so a withdrawal is absent from the JLAP tail as soon as it is absent from `repodata.json`.
