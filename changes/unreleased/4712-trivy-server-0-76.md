- **The scanner adapter's bundled trivy and the trivy server sidecar move together from 0.74.0 to 0.76.0; operators who run their own trivy server must upgrade it to 0.76.0 in the same step as the backend. Published as scanner-adapter 1.5.0** (#4712). In client/server mode (`SCANNER_TRIVY_SERVER`) the adapter refuses to scan unless the server reports the same trivy release as its bundled client: `/probe/ready` stays 503 and every scan fails closed with "client/server mode needs matching releases". The stock `docker-compose.yml`, `docker-compose.local-dev.yml` and `docker-compose.test.yml` now run `ghcr.io/aquasecurity/trivy:0.76.0`, and the Helm chart's `trivy.image.tag` moves in artifact-keeper-iac; a deployment that pins its own trivy server image, or points the adapter at an external one, has to move that pin to 0.76.0 when it takes this release, or scanning stops until it does. The pairing is not a formality: upstream 0.75 and 0.76 changed what client/server mode carries over the RPC. Cryptographic assets found in a scan now travel with the blob and come back with the results (aquasecurity/trivy#11141), and packages keep their modularity label, build info and installed files across the round trip (aquasecurity/trivy#11188); before that, client/server mode silently skipped modular packages on RHEL-family targets that standalone mode detects, and dropped Red Hat SBOM properties. The report's `Trivy.Server` block, from which the adapter reads the server's DB provenance, is unchanged. The bundled binary is `artifact-keeper/trivy` 0.76.0-r1: upstream v0.76.0 on go1.27.2 with no dependency overrides, because 0.76.0 already pins every module the 0.74.0 rebuilds were overriding (grpc v1.84.0, `golang.org/x/net` v0.60.0, and containerd v2.4.1, upstream's own fix for the CVE-2026-95837 that 1.11.1's 0.74.0-r5 patched on the 2.3 line).
