section: Fixed
issues: [#4654, #4593]
---
- **The generic download route now challenges anonymous callers with 401 and accepts an API token as the Basic-auth password** (#4654, #4593). `GET /api/v1/repositories/{key}/download/{path}` answered a request with no credential on a private repository with the existence-hiding 404 and no `WWW-Authenticate` challenge. Clients that only send credentials after a challenge (wget, curl without pre-auth, Maven, most CI fetch helpers) therefore never sent the token they were given, and the user saw a 404 for a file they were entitled to. On top of that, the route sat under the `/api/v1` Basic-auth boundary (#2809), so `username:<api_token>` was refused even when a client did send it; a service account has no password, so for it no Basic credential worked there at all. The route now takes the format routes' contract instead: no credential on a non-public or nonexistent repository answers `401` with the Basic and Bearer challenges (the two cases are byte-identical, so the status is not an existence oracle, as #1808 established for `/maven`, `/npm` and the other package-manager routes), and an API token presented as the Basic password resolves to the token owner with its scopes and repository ceiling intact. A valid credential that is not entitled still gets the existence-hiding 404, a `?ticket=` still rescues a browser download, and a browser navigation still gets the `Bearer` challenge only so the web UI's login flow appears rather than the native Basic dialog. The rest of `/api/v1/*` is unchanged: `/api/v1/auth/me`, `/api/v1/repositories` and every other management route keep refusing the token-as-Basic-password. This matches how Artifactory, GitLab, Nexus and Cloudsmith treat a token on their download URLs while keeping it off their management and identity APIs. No release ever accepted the fallback on this route (#2798 and #2809 both landed before 1.7.0), so this is a deliberate loosening for one data-plane route, not a revert.
